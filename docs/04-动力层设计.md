# 04 · 动力层设计：时序属性绑定 · 规则引擎框架 · Action 绑定模型

> 语义层（docs/01，静态结构）之上的动力层（Kinetic）：让本体「活」起来的三件套。
> 对应调研总结 §1.1 的 Palantir 动力层（Action/Function）+ KnowRob 的规则推理，
> 以及 §7 的时序状态/动态库。

```
时序库(TimescaleDB) ──绑定──► 动态属性(物化) ──读──► 规则引擎(L2) ──结论──► Action 写回 ──Gate A──► 本体图
   (entity,metric)          current_battery/      证明链/优先级       task.dispatch /          CRUD 唯一写路径
   TelemetryMetric 注册表     current_force/...     动作绑定           knowledge.writeback     + ActionLog 审计
```

## 1. 时序属性绑定

**问题**：静态本体回答「能干什么」；当前世界状态（电量/力读数/任务进度）是高频时序，
不落图库。规则引擎需要以「属性」的方式读它，而不是写死 SQL/查询。

**模型（Schema v1.1.0）**：

| 组件 | 声明 | 说明 |
|---|---|---|
| 动态属性槽 | Robot.current_battery / BodyPart.current_force / current_angle / Task.progress（`annotations: dynamic`） | 物化视图声明：不落图库、不入静态 JSON-LD 快照，按需计算 |
| 绑定声明 | TelemetryMetric.binds_to（槽名）+ aggregation（聚合算子）+ window_seconds（窗口） | 「测点 → 属性」的映射写在**本体数据里**，不写死在代码 |
| 聚合算子 | last / avg / min / max / count / rate | Schema 枚举 MetricAggregation |
| 合法性校验 | binds_to 必须是 measures 目标类上的槽 | BindingRegistry.validate_bindings()，装库即查 |

**读取**（`eo/timeseries/binding.py`）：
`BindingRegistry.read(entity, slot)` → 按绑定声明从时序库聚合；
`snapshot(entity)` → 该实体全部动态属性的当前值。
规则引擎经 `RuleContext.dynamic(entity, slot)` 消费；无绑定/无数据 → None（规则安全跳过）。

**写路径**：时序数据仍只写 TelemetryStore（外键 entity_ref + metric_code），
**绝不写回本体图**——动态属性是视图不是存储。

## 2. 自研轻量规则引擎框架

**结构**（`eo/rules/framework.py`）：

| 组件 | 职责 |
|---|---|
| `RuleSpec` | 规则即数据：name/description/category（deduction·constraint·induction·monitoring）/priority/fire/actions（声明式动作绑定） |
| `RuleContext` | 统一上下文：图（nodes/out_links/in_links）、事实（known/assert_）、动态属性（dynamic）、动作（action）、注记（note） |
| `Fact` | (s, p, v) + source（产出规则）+ round + evidence（证明链） |
| `RuleEngine` | 正向链固定点：按优先级序触发 → 增量 trace → 动作写回后自动失效派生事实并再迭代 |

**核心机制**：

1. **证明链**：每条断言带 evidence；`explain(s, p)` 回答「为什么推出这个结论」——
   事实 ← 规则（第几轮）← 证据（图/时序来源）。调研 §6.5「要证明树而不是黑盒答案」落地。
2. **优先级**：同轮内按 priority 降序 + 名称序（确定性）；高优先级先断言，同键先到先得。
3. **动态属性接入**：RuleContext.dynamic 走绑定层——监测规则（category=monitoring）
   能写「力读数 < 5N ⇒ 滑移」这类规则。
4. **规则 → Action 绑定**：
   - 声明式：RuleSpec.actions = [{"action": ..., "params": {...{s}/{p}/{v} 占位符}}]，
     断言新事实时自动触发（参数取自断言事实）
   - 程序式：rule 代码里直接 ctx.action(name, **params)
5. **图变更一致性**：Action 写回使 CRUD.version 递增 → 引擎失效全部派生事实
   （幂等写不触发）→ 再迭代重推（防止「已改图的属性」被旧事实污染）。
6. **兼容层**：`eo/rules/engine.py` 保留 `forward_chain()` tuple 接口；
   旧 `Rule` 对象自动包装成 RuleSpec。

**扩展**：加规则 = 一个 RuleSpec 对象（数据化，可热增改）；领域规则见
`eo/rules/domain.py`（6 条：演绎×3/约束×2/归纳×1）；监测规则示例见
`sim/eosim/scenarios/slip_loop.py`（SLIP_MONITOR_RULE）。

## 3. Action 绑定模型

**问题**：本体的写操作必须受控——谁、对谁、做了什么、结果如何、是否合法。
（Palantir ActionType 思想 + docs/01 ADR-3 审计。）

**模型**（`eo/actions.py`）：

```
ActionType（注册表定义）
  ├─ name / description
  ├─ params（参数规约：名称→类型）
  ├─ targets（可作用的目标 ObjectType）
  ├─ target_param（哪个参数是目标实体 id）
  └─ handler（处理器：内部经 OntologyCRUD 唯一写路径，调用 Gate A/B）

执行管线（Action.execute）：
  ① 参数校验（缺参 → rejected）
  ② 目标绑定校验（存在 + 类型 ∈ targets → rejected）
  ③ handler 执行（写操作经 CRUD → Gate A；校验失败 → failed，状态回滚）
  ④ 自动审计：ActionLog 实体（action_type/actor/target/detail/result）经 Gate A 落库
  → ActionResult {ok, target, messages, patches, audit_log_id}
```

**绑定语义**：

| 绑定 | 含义 |
|---|---|
| Action × 目标实体 | target_param 绑定到本体实体，类型受 targets 限制（如 task.dispatch 只作用于 Task） |
| Action × 校验 | 处理器内部绑定 Gate A（写校验）/ Gate B（可达性+拦截）——校验是动作的组成部分 |
| Action × 审计 | 每次执行自动产生 ActionLog（ActionInstance），幂等续号防冲突 |
| 规则 × Action | RuleSpec.actions 声明式绑定（§2.4）：结论 → 写回闭环 |

**内建动作**（`build_registry` 装配，扩展 `reg.register(Action(...))`）：

| 动作 | 作用 | 绑定校验 |
|---|---|---|
| `task.dispatch` | 可达性+拦截 → 状态迁移 + verdict 写回 | targets=[Task] |
| `task.reassign` | 改派机器人 | targets=[Task] + 目标必须 Robot |
| `task.cancel` | 取消（终态保护） | targets=[Task] |
| `fault.report` | 按模式库上报：建事件+部件置 fault+传播 | targets=[FaultMode] |
| `knowledge.writeback` | 归纳写回（通用受控更新） | Gate A |
| `entity.create` | 受控新建实体 | Gate A |

**验证闭环**（sim slip_loop 场景，三件套集成）：
监测规则读动态属性（current_force=4.0 < 5）→ 断言滑移（带证据）
→ 声明式动作绑定 knowledge.writeback 写回 surface=slippery（Gate A）
→ 审计落库 → 派生事实失效重推（grip_factor=1.5）→ 再下发触发拦截。
